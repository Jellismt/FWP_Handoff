# Data refresh — regs snapshot + reference datasets

Two kinds of bundled data ship inside the web build, each with its own refresh
path. Both produce **committed files** — refresh, verify, commit, then build
the release; the Docker image build itself stays hermetic (no network fetch at
image-build time).

## 1. The bundled regs snapshot (the offline floor)

`web/public/data/regs-snapshot.json` is a build-time export of the
**published** regulations from the Regs Manager public API. It is the offline
floor: what a never-been-online install (especially a fresh mobile install)
shows until it can reach the live API. Online users always fetch live, so
refreshing the floor is low-urgency — it matters for the next app-store build
and for fresh offline installs.

Refresh it:

```bash
cd web
npm run data:regs
```

- `REGS_SNAPSHOT_API_BASE` overrides the regs API host the export reads from
  (build-only environment variable; defaults to the production API and is
  never baked into the app).
- `REGS_SNAPSHOT_YEAR` overrides the season year if needed (defaults to the
  current regs year).
- **Safe by design:** if the API is unreachable, the existing committed
  snapshot is left untouched — a build machine without egress never clobbers
  good data.
- Entries are keyed by the exact cache keys the runtime uses, and enriched
  with honest freshness metadata (`effectiveDate` / `validUntil` / source
  label + publication version).

Then commit the regenerated file. `npm run check:regs-floor` fails verify when the
committed floor is older than 90 days or past its `validUntil`; the mobile build wrapper
prints the same nudge at the moment it matters.

**When to refresh:** after any staff publish you want reflected offline, and
always as part of cutting a mobile store release.

## 2. Reference datasets (`web/public/data/*.json` + manifest)

Non-regulatory, **freshness-tracked** reference data (e.g. hunting-district
facts) is generated by the builders in `scripts/build-data/` from curated
sources, and registered in `web/public/data/data-manifest.json` with
`effectiveDate`, `source`, `schemaVersion`, and an integrity hash.

Regenerate everything:

```bash
cd web
npm run build:data        # runs scripts/build-data/build_all.mjs + provenance annotation
```

- The manifest regenerates with the datasets; its version increments per run.
- Commit the regenerated JSON **and** the manifest together.
- Gates: `npm run check:manifest` (metadata completeness) and
  `npm run check:data-freshness` (hash + freshness integrity) both run inside
  `npm run verify` and will catch a half-committed refresh.

**What the manifest deliberately does NOT track:** static reference geometry
(`montana-boundary`, `major-rivers`, `major-lakes` geojson), the regs snapshot
(its own `check:regs-floor` gate), and the hand-committed
`cwd-check-stations.geojson` are **excluded on purpose** — none has a 12-month
freshness lifecycle. This split, and how each excluded file is covered instead,
is the "Manifest scope" table in
[`scripts/build-data/README.md`](../../scripts/build-data/README.md). Don't force
them into the freshness manifest.

The `usgs-gages` dataset is fetched from the USGS NWIS Site Service at build
time (active Montana stream gages reporting discharge). When the service cannot
be reached the committed catalog is kept and a warning is printed; set
`USGS_GAGES_REQUIRE_FETCH=1` for a release build so a stale catalog fails loudly.

## Updating a dataset's schema

1. Change the source + builder under `scripts/build-data/`.
2. Bump the dataset's `schemaVersion` in the builder's manifest entry.
3. Regenerate (`npm run build:data`), update consumers, run
   `npm run verify`.
